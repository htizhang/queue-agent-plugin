Queueing research in your coding agent

Start where your work already is.

These skills guide your coding agent from data to a queue model to a policy. The two Stages are capabilities, not a pipeline that you must run from end to end. Bring logs, a model, a simulator, or a question, and the entry skill helps your agent choose where to begin.

InstallQueue Agent 0.1.0 installs in Claude Code or Codex with a one-line command. Getting started gives the commands, how to start the entry skill in each host, and a source-use fallback.

  • Straight to Stage 2

    A model that you specify can go directly to Stage 2. If the work needs simulation, the agent builds an evaluator for that model. That needs no new logs and no Stage 1.

  • A simulator is not proof

    An existing simulator does not by itself show that it represents your system. To check or repair that agreement, start with Stage 1.

  • Moving between Stages

    For an end-to-end request, the agent builds on what is already available and moves between Stages as needed. It does not repeat finished modeling work.

  • Discussion stays discussion

    A discussion-only request does not start implementation or experiments. Unrelated tasks do not need either Stage.

Stage 1

Queue modeling

Skill source: skills/queue-modeling/SKILL.md

Stage 1 turns data and a system description into two matching deliverables: a documented queue model and an executable simulator that implements it. The simulator generates trajectories and evaluates the consequences of different policies.

You bring

  • Data: event records, logs, or other observations.
  • A description of the system and how it operates.
  • Optionally, an existing model or simulator to check or revise against the data.

The work

  • Establish what the model represents: jobs, resources, routing, capacity, and the system boundary, plus when decisions occur and what a policy can observe.
  • Read the records before fitting: event meanings, units, logging windows, missing events, and censoring. Arrival-to-departure time includes waiting, so it is not a service-time sample.
  • Implement the simulator with system rules, fitted estimates, replaceable policies, and measurements kept separate. Configurations and random seeds are explicit, and a small case runs early.

You get back

  • A queue model: a self-contained description of the boundary, jobs, resources, state and event dynamics, stochastic mechanisms, parameters, and assumptions. It states when the policy decides, what it observes, and which actions are feasible.
  • The corresponding simulator: code with its fitted configuration and instructions to run it, set randomness, and supply a replaceable policy. It produces trajectories or event records.
  • Concise validation results and the remaining issues that affect use.

Feedback loop

Independent, executable feedback

When the host supports delegation, the skill prefers a separate validation subagent. It receives the original data and system description, the observation definitions, the model description, the candidate simulator, and instructions to run it. It develops its own checks from that evidence instead of confirming the builder’s explanation. It runs the simulator and reports concrete discrepancies, with the observations or test outputs behind them and the steps to reproduce them.

Model–implementation agreement
The simulator’s dynamics, parameters, and policy interface implement the documented model.
Mechanics
Flow accounting, capacity, event order, routing, and action feasibility, with hand-checkable or analytical cases where they apply.
Data agreement
Simulated and observed quantities under matching observation windows, logging rules, and the historical policy, compared distributionally. Held-out data where feasible.
Policy use
Alternative feasible actions keep constraints and information boundaries valid. Supported behavior stays distinct from extrapolation.

The main agent owns integration. It resolves each finding against the evidence, revises the model, the implementation, or both, and reruns the affected checks.

Done when both deliverables exist, the simulator runs through its documented interface, and checks support model–implementation agreement and the intended use. Unresolved failures are reported. Policy work is a separate task: when you request it, the model and simulator go to Stage 2.

Stage 2

Policy design

Skill source: skills/queue-policy/SKILL.md

Stage 2 finds a policy suited to your queue and objective. It first confirms the problem with you, then does the work that problem needs. Designing a new algorithm is one possible task, not the default.

Enter with a Stage 1 handoff

A documented model and its simulator, from earlier modeling work.

Or enter directly

Your own model, simulator, or specified model family. A simulator is optional at entry, and Stage 2 needs no new logs.

First, confirm the problem definition

Queue family
The shared structure and mechanisms, the permitted variation and ranges, and any target instance. One instance does not define a range of other systems.
Objective
The performance measure and its direction, with any weights or aggregation that decide what counts as better.
Constraints
Decision timing, observable information, feasible actions, and the operational requirements that the policy must satisfy.

The agent summarizes what the artifacts and conversation establish, asks short questions about the gaps, and asks whether to proceed. All three parts need your explicit confirmation.

A confirmation that you already gave is reused while the definition is unchanged. An unanswered question stays pending, including in unattended runs. Discussion and reading the inputs can continue, but implementation and experiments wait.

Fixed unless you authorize a change

Policy redesign and parameter tuning stay inside the confirmed definition. Poor results and worker suggestions do not change the family, objective, or constraints. The agent can propose a change and wait for your decision. After you authorize one, it updates the affected evaluator mechanics, metrics, and baselines, and does not reopen the unchanged decisions.

Then choose the work the problem needs

  • Adopt

    An established policy meets the need

    Adopt or explain that policy, and check that it applies to your queue.

  • Compare

    Several applicable policies

    Evaluate them on your objective and select among them.

  • Tune

    Fixed structure, open values

    Tune the parameter values for the target queue or the requested operating range. For simulation-based tuning, the skill points to the external SimOpt project as an optional resource, not a bundled dependency.

  • Design

    A new or improved method

    Improve existing methods or design a new policy within the fixed family.

    See policy discovery

Approaches can be combined. A family definition does not turn an adoption or tuning request into a broad discovery campaign.

Only when needed

Prepare an evaluator

If simulation is needed and no simulator exists, the agent builds one for the specified model. This is evaluator preparation, not Stage 1, and it needs no new logs.

An existing simulator is first checked against the model, the policy interface, the observable information, and the measurements, with small cases. If a check fails, the implementation is repaired against the fixed model. An applicable analytical evaluation can suffice for a simpler request.

Whenever policies are compared

Evaluate on equal terms

  • Every policy gets the same objective, feasible actions, and information assumptions, checked in the code.
  • Published baselines follow their sources, and parameterized baselines get a justified tuning setup.
  • Repeated runs use shared random inputs where appropriate, with fresh replications after tuning when needed.
  • Reported results come from the final code and parameter values, and name the instances tested.
You get back
  • The policy or recommendation, the family it applies to, and the evidence that supports it.
  • For implementation tasks, runnable policy code, concise run instructions, and any new or revised simulator.
  • A self-contained explanation of the decision logic, parameter meanings and units, chosen values and how they were selected, and the important result patterns.
  • Simulated performance kept distinct from established published guarantees.

The handoff matches the depth that you request.

Stage 2 · design branch

Policy discovery

Reference source: skills/queue-policy/references/policy-discovery.md

Discovery is for new or improved policies. It starts after the problem definition is confirmed and any needed evaluator is ready. Adoption, comparison, and fixed-policy tuning do not need it. The confirmed definition governs both loops below.

Outer loop · main agent

  1. ReviewRead the findings across workers and instances.
  2. DiagnoseAsk what limits progress: the mechanism, missing context, an evaluator or baseline defect, noisy comparisons, or an exhausted direction.
  3. AdaptChoose the next research step from the evidence.

Options, not a fixed sequence: let a productive worker continue, supply missing details or a relevant paper, redirect effort, test whether ideas combine, get an independent check, or assign a simplification task. Disappointing results alone do not show that the problem is impossible or that it needs a new definition.

  • Inner loop · development subagent

    1. Hypothesize
    2. Implement
    3. Evaluate
    4. Inspect
    5. Revise

    Owns an iterative research task and revises its approach without waiting for the main agent after every trial.

  • Inner loop · another subagent

    1. Hypothesize
    2. Implement
    3. Evaluate
    4. Inspect
    5. Revise

    Can test a different hypothesis or continue an earlier candidate, at its own pace and in its own files.

Team size is the host’s choice. The host chooses how many workers, which tools, and when to review. Without delegation, the agent performs the same roles in sequence and says so.

At useful checkpoints, workers return their strongest candidates with reproducible evidence, relevant failures, open questions, and a proposed next direction.

For promising candidates

Refine by simplifying

Simplification is policy development. Workers test removing components, consolidating rules, or fixing parameters, and keep the original for comparison. Ablation checks what changes when a component is removed; sensitivity analysis checks what changes when a parameter varies. A flat response in one instance does not show that a parameter can be fixed across the family.

The simpler policy is preferred when the performance difference is practically negligible and the evaluation supports that conclusion.

For the final rule

Check it against literature

The final decision rule is compared with the closest applicable methods, again after simplification or combination changes it. Borrowed components are cited, and the specific modification is described.

If the rule matches a known method, the report says so. An unsuccessful search alone does not establish novelty.

Before delivery

Final verification

The main agent reproduces promising results under one consistent evaluation setup, checks feasibility, and assesses performance across the requested family, not only the cases a worker chose.

Then

Delivery

The Stage 2 policy-and-evidence handoff. If gains remain unconvincing, it reports the best supported result, what was tried, and the open obstacle.

Explicit request only

Discovery Lab: opened only for new-algorithm design

The Discovery Lab holds agent-discovered policies with runnable implementations and bounded evidence. Its entries are research leads, not established recommendations. The Lab is not part of the agent’s default knowledge or of literature retrieval.

The agent reads the Lab index, then only the relevant entries, when you explicitly ask it to design a new algorithm. It keeps that intent for the rest of the new-design task.

Adoption, comparison, fixed-policy tuning, a general request to improve performance, adopting a specified candidate, and suggestions from the agent or its workers do not open the Lab. If you later limit the task to established methods, the agent stops using it.

Lab policies are evaluated under your confirmed definition like any other candidate. Reading the Lab does not authorize writing results back to it. This gate concerns research use: a separate, requested contribution may read the relevant entry to prepare an update.

Shared by both Stages

Literature and writing

Both Stages use these skills, and each also works on its own: a literature question or a writing task does not start modeling or policy experiments.

Literature

Skill source: skills/queue-literature/SKILL.md

Source-grounded answers for modeling and policy decisions. The agent reads the relevant bundled note and its source records first, and searches further only when a material question remains open.

For Stage 1, the topic map covers system primitives, state and dynamics, log semantics, identifiability, statistical fitting, and model validation. For Stage 2, it covers policies such as c-mu, generalized c-mu, SRPT, Gittins, load balancing, maximum pressure, backfilling, and reentrant-line control, plus paired evaluation with common random numbers.

The local notes are a starting point, not a claim of complete prior-art coverage. The Discovery Lab is not part of this retrieval.

Writing

Skill source: skills/asd-ste100/SKILL.md

English model descriptions, policy explanations, and reports for a reader who did not take part in the work. The skill uses STE-flavored prose, based on the ASD-STE100 rules for Simplified Technical English.

It keeps equations, numerical results, citations, assumptions, scope, and claim strength. A wording edit does not change the queue family, objective, constraints, or policy.

The optional linter checks some language patterns. It does not check scientific correctness or reader understanding.

Opt-in

Contribute, only when you ask

Skill source: skills/queue-contribute/SKILL.md

Contribution starts from your request. Finished research, good results, and saved artifacts stay in your workspace unless you ask to contribute them. Contribution is separate from running either Stage.

Your request to contributeThe material’s provenance decides the path, not its publication status.

From published work

Literature knowledge

Published or classical methods, modeling and identification methods, assumptions and applicability conditions, citations, and source-supported practice.

Home
A note and its source records under skills/queue-literature/references/, with a topic-map row for a new note.
Checks
Each substantive claim is checked against its cited source, and the knowledge checks run.
From agent research

Agent-discovered policy

A new policy found through LLM-agent research. It stays on this path after publication or peer review.

Home
An entry under discovery-lab/ with a method description, implementation, and evaluation evidence. See the Lab contribution guide.
Checks
The method is related to the closest known methods, and the cases where baselines win are reported as well.
Publication, only as far as you authorize
  • Local draft
  • Local commit
  • Pushed branch
  • Pull request
  • The agent works on a new branch in a Git checkout of the destination, and stages only the contribution’s files.
  • Before it publishes anything, it inspects the change for unrelated files, private data, credentials, absolute local paths, and bulky artifacts.
  • When the scope is open, it prepares the draft and asks before it pushes.
  • It does not merge or turn on automatic merging. Maintainers decide, and their review is not scientific peer review.

About this page

What this guide is

This page explains the skills and how they connect. It opens from a local copy without a network connection or build step.

The repository is the Queue Agent plugin package. It contains six skills, a startup hook, reference notes, Discovery Lab entries, and the plugin manifests and catalogs for Claude Code and Codex. See Getting started for installation, maintenance, host loading, and source-use instructions.

The hook in hooks/hooks.json gives a short startup orientation that points to the entry skill. It does not choose or store a Stage. Host permissions still control execution; explicit skill selection also works without the hook.

  • Getting started: install the plugin, start a task, and see example requests.
  • README: the skill map and project status.
  • Design decisions and references: why the workflow is shaped this way.
  • Contributing: how to propose literature notes, discovered policies, or workflow changes.
  • Entry skill: the instructions that choose a starting point.

Reading the diagrams

Diagram key

The diagrams borrow the notation of queueing networks. Each skill is a station, and your request is routed to the station that fits.

Station. A skill, drawn as a queueing station: a buffer and a server.
Dispatcher. The entry skill, queue-agent. It chooses a route from your request and the artifacts you have.
Solid arrow. A route or the main flow of work.
Dashed line. Optional, used only when the task needs it: the Stage 1 handoff, an existing model to check, or evaluator preparation.
Dotted line or outline. Opened only on your explicit request: the Discovery Lab and contribution.
Red-pencil arrow. Feedback or iteration: validation findings in Stage 1, and the inner and outer loops of policy discovery.
Cobalt frame. The confirmed problem definition. It stays fixed unless you authorize a change.
Moving dot. When you point to or focus a route on this page, it turns cobalt and a dot moves along it. With reduced motion, the dot appears without moving.
